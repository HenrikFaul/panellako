## Technikai döntések

### Miért csak az overview section-ből lett eltávolítva a cím?
Az overview section közvetlenül a premium header alatt jelenik meg. A header már tartalmazza `buildingName` (h1) + `buildingAddress` (p). A dupla megjelenítés felesleges és zavaró. Az overview helyett a **lakói azonossági blokk** sokkal hasznosabb: a bejelentkezett felhasználó neve, szerepkör badge, és a saját albetét adatai.

### Miért van sidebar és overview link is a profilra?
A sidebar állandóan elérhető (desktop), az overview CTA gombok a fő content flow-ban jelennek meg. Mindkettő más navigációs kontextusban éri el ugyanazt az oldalt — nem redundancia.

### Multi-unit support — architektúra javaslat
A jelenlegi `memberships` UNIQUE constraint: `(profile_id, building_id, role)`.
Ez azt jelenti, hogy egy user azonos roleval nem lehet egyszerre két albetéthez rendelve.

**Jövőbeli migration** (nem ebben a PR-ban):
```sql
-- Alternatív: külön resident_unit_links tábla
CREATE TABLE public.resident_unit_links (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  profile_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  building_id uuid NOT NULL REFERENCES public.buildings(id) ON DELETE CASCADE,
  unit_id uuid NOT NULL REFERENCES public.units(id) ON DELETE CASCADE,
  link_type text NOT NULL DEFAULT 'owner' CHECK (link_type IN ('owner','tenant','co_owner','family','agent')),
  active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (profile_id, unit_id)
);
```

Ez lehetővé tenné, hogy egy tulajdonos több albetétet is kezeljen ugyanabban az épületben.
