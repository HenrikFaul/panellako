# PanelLakó v0.10.6 — Shared GeoData Address Registry

**Dátum:** 2026-08-30
**Branch:** `codex/shared-geodata-address`
**Kapcsolódó provider branch:** WebTools `codex/shared-address-service`
**Típus:** geodata / onboarding / multitenancy / security / reusable platform capability
**Állapot:** implementáció, lokális kapuk és védett Preview deploy PASS; production adatbázis- és end-to-end kapuk a release-folyamatban külön igazolandók

## 1. Mi változott és miért

A PanelLakó új közösség kezdeményezése korábban szabad szöveges címet fogadott.
Ez nem adott megfelelő település-/utca-/házszám-ajánlást, nem biztosított stabil
címidentitást, és túl könnyűvé tette ugyanazon fizikai cím több változatban való
rögzítését.

A megoldás a már létező GeoData Supabase projekt OSM-címállományára épül. A
közös adatforrás a WebToolsban verziózott Address Registry API lett; a
PanelLakó ezt szerveroldali, hitelesített adapteren keresztül fogyasztja. A két
Supabase projekt továbbra is külön felelősségi és biztonsági tartomány.

## 2. Felhasználói felület

- Új, újrahasznosítható `AddressAutocomplete` komponens készült.
- Debounced, megszakítható keresés és stale-response védelem működik.
- A találati lista billentyűzettel kezelhető ARIA combobox.
- Csak magyar, épületszintű találat választható ki.
- A teljes házszám megőrzi a tartományt, toldalékot és épületjelölést.
- Az OpenStreetMap-attribúció a kiválasztott és visszatöltött profilcímen is megmarad.
- Hiányzó címhez explicit kézi review út van; ez nem tesz úgy, mintha a cím ellenőrzött lenne.
- A komponens az onboarding és a lakói profil korábbi, duplikált címkeresését közös logikára cseréli.

## 3. PanelLakó backend és adatbázis

- `GET /api/location/autocomplete` a shared API suggest és reverse műveleteit kompatibilis válaszra alakítja.
- `POST /api/onboarding/community-requests` nem bízik a kliens címmezőiben: a kanonikus UUID-t szerveroldalon újra feloldja.
- `GET/POST /api/user/reference-address` ugyanezt a trust boundaryt használja profilmentésnél.
- A resolve adapter az `EXACT` és az ellenőrzött `LINEAGE_REDIRECT` válaszokat külön kezeli: történeti UUID esetén kizárólag a provider által visszaadott, belsőleg konzisztens aktuális kanonikus UUID menthető.
- A request body olvasás stream-szinten korlátos; hibás vagy hazug `Content-Length` sem kerülheti meg.
- A lookup és onboarding kvóta adatbázisban atomikus és felhasználóhoz kötött.
- A cím-snapshot immutable, verziózott és auditálható.
- A source aliasok a változó külső OSM-azonosítót kanonikus PanelLakó-címhez kötik.
- A `VERIFIED` és `DISPUTED` címeket automatikus forrásfrissítés nem írhatja felül.
- A profil registry-provenance mezőit kizárólag service-role command írhatja.
- A legacy `create_community_creation_request(...)` RPC a phase-1
  kompatibilitási ablakban `PUBLIC` és `anon` számára tiltott, de
  `authenticated` számára ideiglenesen elérhető marad, hogy a jelenlegi éles
  kliens a v2 alkalmazás kiadásáig se veszítsen funkciót. A végleges revoke
  külön closure migráció és hosted v2 smoke után történhet.
- A kérelem önmagában nem ad workspace-, membership-, role-, mandátum- vagy tenantjogot.

## 4. WebTools provider

- Új, idempotens `address_search_v1` projekció a meglévő `osm_addresses` fölött.
- Determinisztikus, aktuális normalizált UUID v5 címidentitás és standard
  `osm:<type>:<id>` forráskulcs.
- Az UUID az aktuális normalizált identitást jelöli; az append-only OSM
  source-lineage a korábbi UUID-k ellenőrzött feloldását és az idempotens
  visszajátszás stabilitását biztosítja.
- Magyar building/postcode szűrés, node/way deduplikáció és legacy OPL escape javítás.
- `pg_trgm` GIN + GiST KNN indexek, 256-os candidate cap és 4,5 másodperces SQL-timeout.
- Három narrow read RPC: suggest, resolve, reverse.
- Versioned HTTP API bearerrel, bemenetkorláttal, biztonságos hibákkal és megfelelő cache/Vary fejlécekkel.
- A consumer RPC-k reapplykor előbb minden korábbi `PUBLIC`/`anon`/`authenticated` grantot elveszítenek, majd csak `anon` kap végrehajtást.
- Az alap- és importtáblák, írások és rebuild továbbra is default-deny.
- Current + previous consumer tokennel megszakítás nélküli rotáció lehetséges.
- Az OSM importer az új `sb_secret_` server keyt kizárólag `apikey` headerként, a legacy JWT service-role kulcsot továbbra is bearerrel kezeli.
- A PanelLakó opcionális Stripe- és push-integrációi kéréskor inicializálódnak;
  hiányzó Preview secret nem akadályozza a címfunkció buildjét, az adott
  integráció pedig konfiguráció nélkül szabályozottan, fail-closed áll le.

## 5. Biztonsági határ

GeoData felé csak publikus címreferencia megy. Nem mehet át:

- felhasználó, lakó vagy tulajdonos;
- session, auth token vagy személyes adat;
- workspace, albetét, tagság, role, capability vagy mandátum;
- onboarding üzleti adat, tenant dokumentum, pénzügy vagy auditrekord.

A PanelLakó a GeoData service-role kulcsát nem kapja meg. A WebTools consumer
kliens szándékosan elutasít service-role és `sb_secret_` credentialt.

## 6. Titokkezelési megállapítás

A két repository történetében korábban követett `.env` fájl szerepelt. A
munkafából való untrack önmagában nem von vissza kulcsot és nem tisztítja a Git
historyt. A release ezért külön, fogyasztó-leltárra épülő rotációs kaput kapott.
A cím consumer token dual-token átmenete és az új Supabase secret-key kompatibilis
importer ennek technikai előfeltétele.

## 8. Kötelező háromfázisú cutover

1. **Kompatibilis séma:** a `20260830120000` migráció először úgy kerül élesre,
   hogy a legacy RPC `PUBLIC`/`anon` joga tiltott, az `authenticated` jog viszont
   ideiglenesen megmarad. Ez alatt a jelenlegi production kliens változatlanul
   tud közösségi kérelmet beküldeni.
2. **v2 alkalmazás:** csak a kompatibilis séma production ledger- és
   privilege-ellenőrzése után kerülhet élesre az új PanelLakó alkalmazás. A
   hosted próba bizonyítja a kanonikus cím kiválasztását, szerveroldali resolve-ot
   és a `create_community_creation_request_v2` sikeres útját.
3. **Closure:** csak a sikeres hosted v2 smoke után készülhet és alkalmazható a
   külön `20260830130000_shared_geodata_legacy_rpc_closure.sql`. Ennek kell
   visszavonnia a legacy signature execute jogát `PUBLIC`, `anon` és
   `authenticated` szerepektől, majd production privilege-canaryval igazolnia a
   lezárást. A closure nincs benne a jelenlegi 18 fájlos manifestben.

Az első és a harmadik fázis nem kerülhet ugyanabba a `db push` pending suffixbe:
az azonnali closure újra létrehozná a DB-first/app-first regressziós ablakot.

## 9. Rollback

- A Panel UI és proxy visszaállítható az előző alkalmazáskiadásra; az új címadatbázis-objektumok additívak.
- A migration fájl forward-only; strukturális visszabontás helyett ellenőrzött adatbázis-backup/PITR az elsődleges helyreállítás.
- A WebTools projekció rebuildelhető, az alap `osm_addresses` állományt nem módosítja.
- Consumer token rotációnál a previous token átmenetileg visszakapcsolható; a régi tokent csak sikeres új-token canary után szabad eltávolítani.
