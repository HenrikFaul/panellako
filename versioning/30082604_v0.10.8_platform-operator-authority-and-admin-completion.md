## 1. Mi változott és miért

A v0.10.7 biztonságos read-first control centert és atomikus command-v2
állapotgépet adott, de a közös HMAC superadmin session nem bizonyított névre
szóló operátort, DB-ből származó capabilityt, AAL2-t vagy four-eyes approvalt.
Emellett a users/features/settings mutation flow-k még nem ugyanazt az atomi,
authenticated DB-RPC authority mintát követték, és az admin manifest több
helyen szétosztott metadata maradt.

A v0.10.8 célja ezért:

1. named Supabase Auth platformoperator és időbeli role/capability authority;
2. read-only legacy break-glass, mutációs fallback nélkül;
3. AAL2 és reason minden célzott governance mutációnál; durable idempotency,
   quota és atomi audit az azt fogadó request/execute/revoke parancsoknál;
4. exact-payload four-eyes approval a kritikus műveleteknél;
5. scoped support governance lifecycle és release attestation;
6. egyetlen typed admin manifest és gazdagabb, fail-visible read DTO;
7. a meglévő adminmodulok és a v0.10.7 command/GTFS invariánsok megőrzése.

## 2. Authority és kompatibilitási határ

### Named operator

`lib/superadmin/operator-authority.ts` a Supabase Auth userből és a
`get_platform_operator_context()` RPC-ből oldja fel:

- az operator profilazonosítót;
- aktív role-okat és capabilityket;
- assurance/AAL állapotot;
- aktív support sessionöket;
- `operator | bootstrap | break_glass | none` módot.

`requirePlatformRead(capability)` named capabilityt fogad el, illetve átmenetileg
read-only legacy break-glass sessiont. `requirePlatformMutation(capability)` csak
named operátort, konkrét capabilityt és AAL2-t enged; break-glass mutációt nem.
Az MFA hiány stabil `MFA_STEP_UP_REQUIRED` kódot és allowlisted account-security
útvonalat ad.

Az egyszeri `bootstrap_first_platform_operator` kizárólag service-role RPC,
csak üres assignment-registry és verified, konfigurált profil mellett fut. Ez
nem állandó env-admin bypass.

### Route-scope

Named read authorityt kapott:

- control center és audit;
- health, stats, settings read és job log;
- users masked read és features read;
- community request read;
- OSM address count;
- a konkrét, fix presetekre korlátozott diagnostics/curl read.

Named AAL2 mutation authorityt kapott:

- user trial update;
- feature update;
- setting update;
- community review és duplicate-resolution authenticated atomi RPC;
- job run;
- GTFS batch import;
- migration approval request/execute;
- a felsorolt governance request/decision/execute/revoke actionök a saját,
  explicit szerződésük szerint.

Ez célzott route-lista. Nem jelent általános hardeninget minden érintetlen legacy
admin route-ra.

### DB authority és state machine

- canonical JSON SHA-256 payload-digest és UTC időnormalizálás;
- időben érvényes role/capability ellenőrzés;
- maximum 15 perces friss AAL2 az app-facing authenticated mutation RPC-kben; a
  support revoke requester/approver-vagy-capability szabályt, a command plane
  route-gate után service-role RPC-t használ;
- per-operator action quota a védett műveleteknél és durable idempotency receipt
  az idempotency-bearing mutation RPC-knél;
- ezek exact retryjánál tárolt result replay, azonos key + eltérő payload esetén
  konfliktus; a decision RPC-k key nélkül, row-lockkal működnek, a support
  authorization szerződése pedig külön;
- approval create/decide/consume exact action/cél/payload mellett;
- self-approval, expired approval, payload drift és double-consume deny;
- operator grant/revoke overlap-, self-revoke- és last-admin védelem;
- support request/approve/reject/revoke/authorize/expire, maximum 60 perces exact
  workspace vagy agency scope-pal és terminal-state reactivation denyjal;
- release attestation exact consumed approval mellett;
- atomi `update_platform_user_trial`, `update_platform_feature` és
  `update_platform_setting` RPC;
- atomi `resolve_platform_community_address_candidate` és
  `review_platform_community_creation_request` RPC DB-digesttel, self-review
  denyjal, domain state-lockkal és kettős domain/platform audittal;
- trial/feature/setting direct write trigger guard;
- append-only trigger az audit-, support-event- és attestation historyn.

Az app-facing context/digest/approval/assignment/support/attestation/mutation
RPC-k az `authenticated` szerepnek futtathatók, és maguk ellenőrzik az operátori
authorityt. A bootstrap és support-session expiry csak `service_role`. A
`service_role` audit/support-event/attestation táblajoga SELECT/INSERT; az
UPDATE/DELETE/TRUNCATE visszavont. Ez nem DB-owner/superuser elleni abszolút
immutabilitási állítás.

## 4. Approval és support határ

Four-eyes approval ténylegesen bekötve:

- operátori assignment grant;
- operátori assignment revoke;
- migration apply;
- release attestation.

A user trial, feature és setting RPC capability + AAL2 + reason + idempotency +
quota + atomi audit védelmet kapott, de nem four-eyes workflow. A dokumentáció
nem tágítja ki rájuk az approval claimet.

A support governance UI/API és az `authorize_platform_support_action` exact-
scope primitive elkészült. Általános tenant support-action consumer,
impersonation, minden tenant action dual attributionje és tenantoldali aktív-
session banner nem része ennek a lezárt szeletnek.

- canonical admin read kliens;
- bounded, validált search/pagination;
- emailmaszkolás;
- private `no-store`;
- nyers DB-hiba nélkül.

- same-origin, JSON és bounded body;
- UUID, strict allowlist és reason;
- session-stabil idempotency key;
- named operator/capability/AAL2;
- authenticated Supabase RPC, direct write nélkül;
- DB-oldali canonical digest, receipt replay/conflict és audit;
- stabil not-found/no-op/invalid error contract;
- frontend loading/error/retry, MFA step-up és false-success tiltás.

## 7. Megőrzött v0.10.7 invariánsok

- `20260830130000-v2` command receipt csak egyező `request_payload` mellett
  játszik vissza befejezett `status` + redaktált `safe_result` értéket;
- eltérő payload ugyanazzal a keyjel konfliktus;
- kézi job, migration és GTFS batch ugyanazt a globális
  `platform:mutations` lockot használja;
- lease maximum 15 perc;
- begin/complete/expire a command, kompozit joblog és audit állapotát atomikusan
  kezeli;
- kliens idempotency keyje transportbizonytalanságnál és tabfrissítésnél stabil;
- GTFS guard maximum 500 soros batchre vonatkozik, nem teljes fájlra;
- a GTFS post-chain mindkét job HTTP- és `ok === true` szerződését ellenőrzi.

## 10. Rollback és kockázat

- Az authority UI és named route integration alkalmazás-szinten visszaállítható,
  de break-glass mutációra nem tágítható.
- Mindkét admin migráció forward-only. Audit/history, assignment, approval,
  support-event, attestation és command rekord nem törölhető rollback címén;
  sémahiba újabb forward-fix migrációt igényel.
- Production migráció hiányában a named mutation plane fail-closed; közvetlen
  legacy service-role write nem elfogadható fallback.
- A globális command lock szándékosan konzervatív. Párhuzamosítás csak
  bizonyított resource-lock mátrix után engedhető.
- A support session schema nem production tenant-access bizonyíték. Hosted
  két-tenant negative canary és konkrét consumer integration nélkül marad HOLD.
- Release attestation sor létrehozása nem deploy. Production PASS csak valódi
  deployment ID, commit/artifact/manifest/migration identity és hosted smoke
  mellett állítható.
- Az approval/support decision terminális állapotát a quota-fogyasztás előtt
  ellenőrzi, így az already-decided replay nem meríti a döntési quotát.
- Az `authorize_platform_action` replay nem duplikál authorization auditot, a
  support decision lazy-expiry és maintenance-expiry útja pedig egyaránt support-
  eventet és platformauditot ír. Mindkét invariánst runtime canary bizonyítja.
